# Working in Pith Desk

Read the relevant code, `README.md` and `docs/TESTING.md` before changing behavior. Use `rg` and targeted file reads. Prefer RTK for supported shell commands; use `rtk proxy` or raw output when exact output is necessary. Do not prefix shell syntax or builtins with RTK.

Use Ponytail's `full` principles for development. Read `.agents/skills/ponytail/SKILL.md` when available; use `.agents/skills/ponytail-review/SKILL.md` for requested reviews. These skills are project-local and Git-ignored. Understand the affected flow and callers first, then make the smallest complete, readable change. Reuse existing code, components and dependencies; do not add unrequested features, speculative abstractions or configuration. Preserve validation, data-loss protection, security and accessibility. Test concrete risky behavior and complete the affected checks below.

- Keep the Go + Pith + TypeScript + MyGo stack. Desktop and Server share the Agent core, business logic and Web UI. Preserve both modes and existing user data; do not restore a third Preview mode.
- The Web UI is source-controlled in `frontend/src` with React 19, Vite, Tailwind CSS v4 and shadcn/ui (Nova, Radix). Keep the chosen libraries: Lucide icons, Motion animation, react-resizable-panels, dnd-kit and Zustand. Do not add a second icon, animation, layout, drag or state library.
- shadcn components live in `frontend/src/components/ui`; adjust them there instead of layering presentation overrides elsewhere. Application composition lives in `frontend/src/components`, state projection in `frontend/src/stores`, and requests, permissions, persistence and operation targets in `frontend/src/actions` and Go.
- Express Desktop/Server availability through semantic state in the action layer. Components render that state and emit intents; they do not grow independent business rules. Preserve the generated transport contract from Go.
- Check actual capabilities and behavior rather than one source-code spelling. Permit safe equivalent syntax; retain type, native ingress and security checks. Add behavior coverage for a concrete gap instead of increasing source-shape restrictions.
- Start daily work with the relevant fast checks and focused behavior tests. Before delivery, complete the necessary full validation for the affected surfaces, including browser, native or concurrency checks when applicable. Preserve key regression coverage; do not remove assertions merely to shorten a run. Commands and preparation belong in `README.md` and `docs/TESTING.md`.
- CI always returns the existing `mac` status; do not skip the workflow with path filters. Scope PR checks from their actual base diff, expand coverage for dependencies, public contracts, build/workflow configuration or unknown history, and keep main/manual validation complete. Release tags require a successful complete Check for that exact main commit.
- Install each dependency tree and build the UI once per job. Run the complete Go suite once with race detection in full CI, retaining vet, both browsers and Desktop/Server cross-compilation. Cache downloads and compiled packages, never use cached product output as validation. Refresh Go build caches after source changes; report measured execution and queue time separately and label unmeasured savings. Cancel superseded PR runs, not required main/release validation.
- Keep tasks independent of browser lifetime. Preserve authenticated access, exclusive Server leases and non-replayed writes across refresh, disconnect and takeover. Validate untrusted native and network input at their boundaries.
- Verify with isolated application data and disposable workspaces for mutating tests. Existing workspaces can contain real files even with an isolated profile. Keep temporary reports, screenshots, profiles, fixtures and build artifacts out of commits.

Report local checks, native acceptance and product release as separate facts. A source preview or successful build does not prove a published or deployed artifact.
